For the first few years of my career, I measured my output in pull requests. More code shipped meant more value delivered. I was wrong.

The best engineers I've worked with don't just write code — they question whether the code should be written at all.

## Code is a means, not an end

Every line of code is a liability. It needs to be maintained, tested, debugged, and eventually replaced. The question isn't "how do I build this?" — it's "should we build this, and if so, what's the smallest version that validates the idea?"

This shift in thinking changed how I approach every project.

## Talk to users (or at least watch them)

I used to build features based on specs and call it done. Now I try to understand who will use it and why. Sometimes that means sitting in on user interviews. Sometimes it means watching session recordings. Sometimes it just means asking "what problem does this solve?" in a planning meeting.

You don't need to become a product manager. But understanding the context behind a ticket makes you dramatically more effective.

## Say no more often

The hardest skill I've developed isn't technical — it's learning to push back on scope. Not every edge case needs handling on day one. Not every feature request is worth the complexity it introduces.

A product engineer's job is to find the intersection of what users need, what's technically sound, and what can ship in a reasonable timeframe.

## Own the outcome, not just the output

Shipping a feature isn't the finish line. Did it actually solve the problem? Are people using it? Did it break something else? Following through after launch is what separates feature factories from product teams.

---

I don't think "product engineer" should be a special title. It should be the default way engineers think about their work.
